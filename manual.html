1. How to use this manual

Two kinds of knowledge live in a managed database product, and confusing them is expensive.

One kind belongs to Postgres. Window functions, NULL semantics, index selection, row-level security, transaction isolation. Learn it once and it follows you from a laptop to Neon to Supabase to Aurora to a machine in a rack. Twenty years from now it will still be worth something.

The other kind belongs to a company. Branch naming conventions, a proprietary dashboard, an SDK's idea of a migration, a billing unit invented last quarter. Useful while you stay, worthless the day you leave, and occasionally worthless before that because the vendor was acquired.

Every drill on the practice floor carries a colour that tells you which sort of work you are doing. Blue leaves with you. Magenta stays behind. Each platform card carries a transfer rating estimating that split. Those ratings are editorial judgements about query-language portability and migration cost, arrived at by reading migration paths rather than marketing pages, and you should argue with them.

Suggested rhythm. Complete the eight floor drills in order before opening a single vendor account. Roughly ninety minutes if SQL is already familiar, a full afternoon if it is new. Only then pick one machine and work through its brief. Resist doing three at once; the platforms differ in ways that blur together when sampled in parallel.

What you need. A browser with WebAssembly, which means any browser released since about 2018. Nothing else. No install, no account, no connection string, and no data leaving the tab.

2. What a database is, and what Postgres is

A database is an organised collection of data, held so that questions can be asked of it. A database management system, or DBMS, is the program that holds it and answers the questions. Everyday speech collapses the two, and this manual does as well except where the difference matters.

Postgres — formally PostgreSQL, and "Postgres" everywhere except its own documentation — is a relational DBMS. Work began at Berkeley in 1986 under Michael Stonebraker as the successor to Ingres, hence the name. It has been open source since 1996, is owned by nobody, and is governed by a global development group. Nothing about it is new. Fourteen companies now sell it as a service precisely because it is old, free, and has stopped surprising people.

Relational means it implements Codd's model: data held as values in tables, questions expressed as operations on whole sets of rows, and no way to reach the data except through those operations. Section 11 tests Postgres against Codd's twelve rules one at a time and finds three of them wanting, which is the useful part.

SQL is the language you ask questions in. Pronounced either "sequel" or as three letters; nobody minds. Developed at IBM in the 1970s as an implementation of Codd's ideas, standardised since 1986, and diverging from his model in several places he objected to publicly. Every product in this field speaks it, which is why learning it transfers.

3. The vocabulary, in order

Twelve units. Each introduces its terms, shows a worked example you can run on the practice floor, then asks you to write one variation. Answers follow each exercise, so read straight through if you prefer.

Where a SQL term corresponds to something in the relational model, the correspondence is given, along with any divergence. Those divergences are not incidental — they are where most confusion in practice comes from.

3.1 Table, row, column

A table holds one kind of thing. This database has two: vendors, holding companies that sell databases, and rounds, holding funding events.

A row is one of those things — one company, one funding event. A column is one fact recorded about every thing in the table: its name, its owner, the amount raised.

Relational correspondence: table is SQL's word for a relation, row for a tuple, column for an attribute. One divergence matters. A relation is a set, so it cannot contain duplicates; a SQL table permits them, making it a bag. Codd treated this as a defect, and rule 2 in section 11 demonstrates it.

Example. The asterisk means every column.

select * from vendors;

Fourteen rows come back, one per company, with every column shown.

Exercise. Show everything in the other table, rounds.

select * from rounds;      -- seven rows

3.2 Query, statement, clause, keyword

A query is a question put to the database. A statement is one complete instruction, ended by a semicolon; a query is one kind of statement, and there are others that change data rather than read it.

A statement is built from clauses, each beginning with a keyword. In select * from vendors, the select clause says which columns, the from clause says which table. Keywords are conventionally written in capitals in textbooks; this manual writes them lower case, and Postgres accepts either.

A result set is what comes back: rows and columns, itself shaped like a table. That closure — questions about tables returning tables — is what allows queries to be built out of other queries.

Example.

select name from vendors;

Exercise. Write a statement returning only the engine column from vendors.

select engine from vendors;

3.3 Projection: choosing columns

Projection is the relational operation that keeps some attributes and discards the rest. SQL spells it as the list of columns after select, separated by commas. Column names take no quotation marks.

Order is yours to choose and need not match how the table was defined.

Example.

select name, owner from vendors;

Exercise. Return the name and the billing unit of every vendor, billing unit first.

select billing_unit, name from vendors;

3.4 Data types and domains

Every column has a data type, fixing what may be stored in it. text for words, integer and numeric for numbers, boolean for true and false, date for dates, jsonb for structured documents. Postgres refuses anything that does not fit, at write time.

Relational correspondence: Codd's domain is the pool of permissible values for an attribute. Data types implement part of that idea. Codd wanted domains to be user-definable and semantically meaningful — a "price" domain distinct from an "age" domain even though both are numbers — so that comparing them would be rejected. SQL's types are cruder, though Postgres offers create domain and custom types for those who want the stricter version.

Practical consequence: text values are written in single quotes, column names are written bare. where owner = 'Amazon' compares the owner column against the text Amazon. Reverse the quotes and Postgres will report that no column named Amazon exists, which is the single most common beginner error and always means this.

Example.

select name, funding_usd_m from vendors where owner = 'Amazon';

Exercise. Return the name and engine of vendors whose engine is sqlite.

select name, engine from vendors where engine = 'sqlite';

3.5 Restriction: choosing rows

Restriction — Codd's term; most textbooks say selection, confusingly, since SQL's select does projection — keeps rows satisfying a condition and discards the rest. SQL spells it where.

A predicate is the condition itself: an expression evaluating to true, false, or unknown. Operators available include =, <> for not-equal, <, >, <=, >=, and like for text patterns. Predicates combine with and, or, not.

Example.

select name, funding_usd_m
from vendors
where funding_usd_m > 50 and engine = 'postgres';

Exercise. Return vendors that are wire compatible and independently owned. The relevant columns are wire_compatible, a boolean, and owner.

select name from vendors where wire_compatible and owner = 'independent';

Note the boolean needs no comparison. where wire_compatible reads as the condition it already is; = true is legal and redundant.

3.6 NULL, and why it is contested

Some cells hold NULL, meaning the value is unknown. Distinct from zero, distinct from an empty string, and available for every data type.

Relational correspondence: none, in the original model. Codd added missing information later and argued in 1986 for two marks — missing-but-applicable and missing-and-inapplicable — because "we have not been told this company's funding" and "this company cannot have funding" are different facts. SQL provides one mark for both. Rule 3 in section 11 records this as the failure it is.

Three consequences you must absorb now, because they cause silent wrong answers rather than errors:

  1. Comparison never works. = null yields unknown, never true, so it matches nothing. Ask is null or is not null.
  2. Sorting puts NULL last ascending and first descending. A "top three by funding" query without care returns three blanks.
  3. Aggregates skip it. count(*) counts rows; count(column) counts non-null values in that column. The gap between those two numbers tells you how much you do not know.

Example.

select (null = null) as "null = null",
       (null is null) as "null is null";

The first returns NULL, the second true.

Exercise. Return the names of vendors with no recorded funding figure.

select name from vendors where funding_usd_m is null;      -- seven rows

3.7 Ordering and limiting

order by sorts the result. Ascending by default, desc for the reverse, and nulls first or nulls last to override where the unknowns land. limit caps how many rows come back.

Relational correspondence: none, deliberately. A relation is a set and sets are unordered, so ordering belongs to presentation rather than to the data. Nothing about the stored table changes. This also means limit without order by returns arbitrary rows, and can return different rows on the next run.

Example.

select name, funding_usd_m
from vendors
where funding_usd_m is not null
order by funding_usd_m desc
limit 3;

Exercise. List every vendor alphabetically by owner, then by name within each owner.

select owner, name from vendors order by owner, name;

3.8 Aliases

as renames a column in the result. Useful when a column carries a computed value with no natural name, or when the underlying name is unhelpful. Table aliases work the same way and save typing in joins: from vendors v lets you write v.name.

Quote an alias in double quotes when it contains spaces. Note the asymmetry: single quotes mean a text value, double quotes mean an identifier.

Example.

select name as company, funding_usd_m as "millions raised"
from vendors
where funding_usd_m is not null;

Exercise. Return each vendor's name aliased as firm, and its billing unit aliased as charged by.

select name as firm, billing_unit as "charged by" from vendors;

3.9 Keys

A primary key is a column, or set of columns, whose value identifies a row uniquely. vendors.id is one. Postgres enforces it: no duplicates, no nulls.

A foreign key is a column holding a primary key value from another table, recording a relationship. rounds.vendor_id holds vendors.id values, so each funding round points at the company that raised it. Postgres enforces this too, refusing rounds that reference a company that does not exist.

Relational correspondence: direct, and this is Codd's rule 2. Give the table, the primary key value, and the column, and any single datum in the database is reachable. Where a table has no primary key the guarantee lapses, which is why duplicate rows are a real problem rather than an aesthetic one.

Example.

select id, name from vendors where id = 1;

Exercise. Return every row from rounds belonging to vendor 2.

select * from rounds where vendor_id = 2;      -- two rows

3.10 Joins

A join combines rows from two tables by matching values, normally a foreign key against a primary key. Written as join ... on <condition>.

An inner join, the default, keeps only rows that match on both sides. A left join keeps every row from the left table, filling with NULL where the right side has nothing — which is how you find the absences.

Relational correspondence: Codd's join, and it is the operation that makes the model work. Splitting data across tables and rejoining on demand avoids storing the same fact twice, which is what normalisation means and why it prevents a fact being updated in one place and left stale in another.

Example.

select v.name, r.stage, r.amount_usd_m
from rounds r
join vendors v on v.id = r.vendor_id;

Exercise. List every vendor together with its round count, including vendors that have raised nothing recorded.

select v.name, count(r.id) as rounds
from vendors v
left join rounds r on r.vendor_id = v.id
group by v.name
order by rounds desc, v.name;

Note count(r.id) rather than count(*): after a left join, count(*) counts the padded row and reports 1 where the truth is 0.

3.11 Aggregates and grouping

An aggregate function collapses many rows into one value: count, sum, avg, min, max. Without grouping it collapses the whole table to a single row.

group by splits rows into groups first and applies the aggregate to each, returning one row per group. having then filters the groups, and where cannot do that job because it runs before grouping exists.

Clause execution order, which differs from writing order and explains most confusing errors:

from → where → group by → having → select → order by → limit

Example.

select engine, count(*) as vendors, sum(funding_usd_m) as disclosed
from vendors
group by engine
order by vendors desc;

Exercise. Count how many vendors each owner has, keeping only owners with more than one.

select owner, count(*) as n
from vendors
group by owner
having count(*) > 1;

3.12 Views, indexes, constraints, transactions

Four terms you will meet constantly and need not use yet.

A view is a stored query given a name, queried as though it were a table. Codd's derived relation. Views let the underlying tables be restructured while queries carry on working, which is rule 9.

An index is a data structure making lookups faster. It has no logical meaning whatsoever: adding or dropping one never changes any answer, only the time taken. That invariance is Codd's rule 8, and it is why an index is a maintenance decision rather than a modelling one.

A constraint is a rule the database enforces on every write — a check, a uniqueness requirement, a foreign key. Declared once, applied to every writer forever, including writers not yet written. Codd's rule 10 requires constraints to live in the catalog rather than in application code, and the reason is exactly that: validation in an application protects only the paths someone remembered.

A transaction is a group of statements that succeed or fail together. begin, then your statements, then commit to keep them or rollback to discard. Nobody else sees a partial state.

Example.

create view portable as
  select name, engine from vendors where wire_compatible;
select count(*) from portable;

Exercise. Create a view named funded showing name and funding for vendors with a disclosed figure, then count its rows.

create view funded as
  select name, funding_usd_m from vendors where funding_usd_m is not null;
select count(*) from funded;      -- seven

3.13 DDL, DML, and the catalog

Statements divide into two families. DDL, data definition language, changes the shape of the database: create table, alter table, drop, create index, create view. DML, data manipulation language, changes or reads the contents: select, insert, update, delete.

The catalog is where Postgres records the shape of everything — tables, columns, types, constraints, indexes, views. It is itself made of tables, queryable with ordinary SQL. Codd's rule 4, and the most satisfying of the twelve: the database describes itself in its own language, with no separate metadata dialect and no privileged inspection tool.

Example.

select table_name, column_name, data_type
from information_schema.columns
where table_schema = 'public'
order by table_name, ordinal_position;

Exercise. List the names of every table in the public schema, using the catalog.

select tablename from pg_tables where schemaname = 'public';

That is the whole vocabulary the rest of this manual uses. Section 5 gives you a route through it; sections 6 to 9 drill each idea until it holds.

4. Warm-up: what you are actually training on

4.1 Postgres in a browser tab

Practice floor drills run against PGlite, a build of Postgres 17 compiled to WebAssembly by ElectricSQL, weighing under 3MB gzipped. Earlier attempts at browser Postgres booted a Linux virtual machine and then ran the server inside it. PGlite drops that layer and compiles the database directly, which is why it starts in well under a second.

Real planner, real type system, real aggregate functions, and dynamic extension loading that includes pgvector and PostGIS. Queries you write here behave as they would against a managed instance, with three caveats worth internalising early:

  • Single connection. Postgres normally forks a process per client. Emscripten cannot fork, so PGlite runs single-process. Concurrency behaviour therefore cannot be exercised here, and drills involving locking or isolation belong on a real server.
  • Single JavaScript thread. A heavy query blocks the page. Production embeddings of PGlite move it into a Web Worker.
  • Superuser everywhere. You connect as postgres, who bypasses row-level security. Drill 8 teaches you to write a policy; verifying that a policy actually blocks someone requires a second role on a real server.

4.2 Why wire compatibility organises the entire market

Postgres speaks a documented protocol over TCP. Any product that implements that protocol can be addressed by every existing Postgres client, driver, ORM, dashboard, backup tool and migration framework, without any of them being modified.

Consequences follow directly. A vendor claiming Postgres compatibility inherits three decades of surrounding software for free. A customer choosing that vendor keeps a credible exit, because a competitor speaking the same protocol accepts a pg_dump without translation. Competition therefore concentrates on operational qualities — provisioning speed, idle cost, branching, region topology — rather than on query language.

Which is exactly why the products that reject the protocol deserve close reading. DynamoDB and Convex both give up portability deliberately and in exchange offer something the compatible field cannot. Judge that trade honestly in both directions.

4.3 The seed data

Both tables describe the managed database market itself, as reported on 27 July 2026.

vendors (id, name, owner, engine, wire_compatible, billing_unit,
         funding_usd_m, valuation_usd_m, meta jsonb)   -- 14 rows
rounds  (id, vendor_id, stage, amount_usd_m, lead_investor, closed_year)  -- 7 rows

Only figures stated in the source reporting appear. Everything undisclosed is NULL. That decision makes the dataset harder and considerably more honest, because most of the difficulty in production SQL comes from absent values rather than from clever joins. Several drills exist purely to make you handle them.

5. The training pathway — seven sessions

Sections 6 to 9 are reference material, organised by topic. This section is the route through them, organised by time. Follow it in order.

Every drill link below opens the practice floor at that exercise. Extension exercises carry no automatic checking, so run them in the scratch console at the top of the page and compare against the answers given here. Self-checks are questions to answer aloud before moving on; if one stalls you, the coaching notes in the relevant block will unstick it.

Total time: about five hours across seven sessions. Spread over a week beats a single sitting, because the material rewards sleeping on it.

Session 0 · Orientation — 15 minutes

Do this. Open the practice floor. Wait for the status line to read Postgres ready. Run the query already in the console, then press Show schema and read both table definitions properly, including which columns permit nulls.

Now run one query of your own invention. Anything. Getting a syntax error and fixing it inside the first five minutes sets the right expectation for everything that follows.

Read. Sections 1 and 2 of this manual, about ten minutes.

Self-check. Why does a browser tab containing a full Postgres engine matter for learning? Why can this engine never teach you about lock contention?

Session 1 · Reading rows — 35 minutes

Objective. Filter and order rows, and stop being surprised by NULL.

Drills. Drill 1 — Filter on a boolean · Drill 2 — Sort, then cut

Attempt each before reading its coaching note in section 4. Getting drill 2 wrong the first time is the intended experience; the reason it fails is the entire lesson.

Extension exercises (scratch console, no checker):

1a. Count vendors by owner, most first.

select owner, count(*) as n from vendors group by owner order by n desc;

1b. List vendors whose billing unit mentions a request or an operation.

select name, billing_unit from vendors
where billing_unit ilike any (array['%request%','%operation%']);

ilike is case-insensitive matching; any over an array saves a chain of or.

1c. Every vendor with its funding shown as a readable string, using 0 where undisclosed. Then do it again preserving the distinction between zero and unknown.

select name, coalesce(funding_usd_m, 0) as funding from vendors;
select name, coalesce(funding_usd_m::text, 'undisclosed') as funding from vendors;

Second version is almost always the right one. Substituting 0 for "we do not know" invents a fact, and downstream nobody can tell which zeros were real.

1d. Vendors whose valuation is unknown, written two ways. Explain why only one works.

select name from vendors where valuation_usd_m is null;   -- correct
select name from vendors where valuation_usd_m = null;    -- returns nothing, ever

Self-check. What does count(valuation_usd_m) return, and why does it differ from count(*)? If wire_compatible allowed nulls, would where wire_compatible and where not wire_compatible together cover every row?

Session 2 · Combining tables — 45 minutes

Objective. Join with intent, aggregate with the execution order in mind.

Drills. Drill 3 — Join across the foreign key · Drill 4 — Aggregate, then filter the groups

Extension exercises:

2a. Every vendor together with its round count, including vendors that have raised nothing recorded.

select v.name, count(r.id) as rounds
from vendors v left join rounds r on r.vendor_id = v.id
group by v.name order by rounds desc, v.name;

Note count(r.id) rather than count(*). After a left join, count(*) counts the padded row and reports 1 where the truth is 0.

2b. Vendors with no recorded round, written three ways.

select v.name from vendors v left join rounds r on r.vendor_id=v.id where r.id is null;
select name from vendors v where not exists (select 1 from rounds r where r.vendor_id=v.id);
select name from vendors where id not in (select vendor_id from rounds);

All three agree here. Insert a row into rounds with vendor_id set to null and run them again: the third silently returns nothing. not in against a set containing a null yields unknown for every row. This trap has taken down production reports; meeting it in a scratch database is much cheaper.

2c. Lead investors appearing in more than one round.

select lead_investor, count(*) from rounds
where lead_investor is not null
group by lead_investor having count(*) > 1;

2d. For each engine type, how many vendors disclosed funding and how many did not, in a single row per engine.

select engine,
       count(*) filter (where funding_usd_m is not null) as disclosed,
       count(*) filter (where funding_usd_m is null)     as undisclosed
from vendors group by engine order by engine;

filter is cleaner than sum(case when ... then 1 else 0 end) and reads as what it does.

Self-check. Why does where fail when you reference count(*)? Which of your three anti-join spellings would you put in production code, and why?

Session 3 · Beyond SQL-92 — 55 minutes

Objective. Window functions and JSONB, the two features that most often replace application code with a query.

Drills. Drill 5 — Rank inside a partition · Drill 6 — Reach into JSONB

Longest session on the floor. Both features have a syntax hurdle in front of a simple idea.

Extension exercises:

3a. Each funded vendor with its funding, plus that engine's total, on the same row.

select name, engine, funding_usd_m,
       sum(funding_usd_m) over (partition by engine) as engine_total
from vendors where funding_usd_m is not null order by engine, funding_usd_m desc;

Compare against group by. Aggregation collapses rows; a window keeps them and attaches the aggregate alongside. Recognising which one a question wants is the skill.

3b. Each vendor's share of its engine's disclosed funding, as a percentage.

select name, engine,
       round(100 * funding_usd_m / sum(funding_usd_m) over (partition by engine), 1) as pct
from vendors where funding_usd_m is not null order by engine, pct desc;

3c. Rounds in chronological order with a running total, and the gap to the previous round.

select stage, closed_year, amount_usd_m,
       sum(amount_usd_m) over (order by closed_year nulls first) as running,
       closed_year - lag(closed_year) over (order by closed_year nulls first) as gap
from rounds where amount_usd_m is not null;

3d. Every distinct key present across all meta documents, with how many vendors carry it.

select k, count(*) from vendors, lateral jsonb_object_keys(meta) as k
group by k order by count(*) desc;

lateral lets a set-returning function see each row's own column. Note which keys appear in three or four rows; those are the candidates to promote into real columns.

3e. Every vendor supporting scale-to-zero, using containment, then using extraction, and explain which you would index.

select name from vendors where meta @> '{"scale_to_zero":true}';
select name from vendors where meta ->> 'scale_to_zero' = 'true';

Self-check. Why does where rn = 1 fail without a CTE? What would rank() change about drill 5's answer if two vendors in one engine had identical funding?

Session 4 · Operating — 50 minutes

Objective. Stop treating the database as a black box.

Drills. Drill 7 — Create an index and read the plan · Drill 8 — Write a row-level security policy

Extension exercises:

4a. Watch the planner refuse your index, then make it change its mind.

explain analyze select * from vendors where engine = 'postgres';
create table big as select (random()*1000)::int as g, md5(random()::text) as payload
  from generate_series(1, 200000);
analyze big;
explain analyze select * from big where g = 500;   -- Seq Scan
create index idx_big_g on big (g);
analyze big;
explain analyze select * from big where g = 500;   -- Bitmap Heap Scan

Same query, same index, different decision, driven entirely by table size and selectivity. Measured in this engine: roughly 23ms falling to under 1ms across 200,000 rows, for about 180 matches.

Expect a Bitmap Heap Scan rather than a plain Index Scan. Postgres collects matching locations first and then visits the heap in physical order, which beats jumping around when a query returns hundreds of scattered rows. Both count as using the index; reading which node appeared and asking why is the habit to build.

4b. A partial index, and confirming it gets used.

create index idx_big_low on big (payload) where g < 10;
explain analyze select payload from big where g < 10 order by payload limit 5;

Partial indexes cost a fraction of a full one when queries reliably carry the same predicate.

4c. Find indexes nobody uses.

select relname, indexrelname, idx_scan from pg_stat_user_indexes order by idx_scan;

Run this against any real system you own. Every unused index taxes writes and, on consumption billing, appears on an invoice.

4d. Write a tenant policy properly, with both clauses.

create table docs (id serial primary key, tenant text not null, body text);
alter table docs enable row level security;
create policy tenant_rw on docs for all
  using      (tenant = current_setting('app.tenant', true))
  with check (tenant = current_setting('app.tenant', true));
select * from pg_policies where tablename = 'docs';

Drop the with check clause and describe precisely what an attacker could then do. Answer: read nothing outside their tenant, and write rows into anyone's.

Self-check. Why did the planner ignore idx_vendors_engine? Whom does enable row level security fail to constrain, and what additional statement fixes that?

Session 5 · Unassisted assessment — 60 minutes

No links, no coaching notes, no reference answers in this manual. Work in the scratch console, closed-book, and verify your own results by reasoning about them rather than by checking against something.

  1. Which engine types have every one of their vendors wire-compatible? Return the engine and the vendor count.
  2. Rank funded vendors by funding within their ownership category (Amazon, Databricks, independent, other), showing ties as equal ranks with no gap afterwards.
  3. Total disclosed round money per vendor, listing every vendor including those with none, showing 0 rather than null for the empty ones, ordered largest first.
  4. Every vendor whose meta carries three or more keys, with the key count.
  5. Add a region text[] column to vendors, populate three rows, then return vendors available in a region you choose. Which index type suits an array containment query?
  6. Create a table with a check constraint that makes an invalid state impossible to store, then prove it by attempting an invalid insert. Explain why a constraint beats validation in application code.
  7. Write a query whose result is correct today and would silently become wrong if a new vendor were added with a null engine. Then repair it.

Question 7 is the one that matters. Producing correct SQL is ordinary competence; anticipating how your SQL will fail as the data changes is the thing worth certifying.

Standard. Five of seven, unaided, is a genuine pass. Question 7 answered well is worth more than the other six together.

Session 6 · First machine — 90 minutes

Only now open a vendor account, and open exactly one.

Choosing. Building something with realtime updates or multi-user auth, pick Supabase and spend the session on RLS, which you have already half-learned. Working in a team with pull requests and preview deployments, pick Neon and spend it on branching. Sitting inside a corporate procurement process, pick Aurora and spend it on IAM and VPC, because that is what the work will actually be.

Follow the training session in section 9 for whichever you chose.

Afterwards, write down three things before the impressions fade: what the platform made easy that was hard before; what it made hard that was easy before; and what you would have to rebuild if you left. Third answer is your own transfer rating, and it will be better calibrated than the estimate on the card because you will have earned it.

6. Block A — Reading rows

Drill 1 · Filter on a boolean

Brief. Name and engine of every vendor speaking the Postgres wire protocol.

select name, engine
from vendors
where wire_compatible;

Returns 8 rows.

Coaching. A boolean column needs no comparison. where wire_compatible = true works and marks you as someone who learned SQL through another language's habits. Postgres accepts the bare predicate because a boolean expression is already a condition.

Watch the third state. where not wire_compatible returns rows that are explicitly false, and silently drops any row where the column is NULL. Here the column is not null, so nothing hides. On a table without that constraint, the two clauses would not partition the table between them, and the missing rows would go unnoticed for months.

Drill 2 · Sort, then cut

Brief. Three vendors with the largest disclosed funding, name and figure, largest first.

select name, funding_usd_m
from vendors
where funding_usd_m is not null
order by funding_usd_m desc
limit 3;

Returns: Redis 357, Neon 129.6, MotherDuck 100.

Coaching. Omitting the where clause is the whole point of this drill. Postgres sorts NULL as larger than any value, so under desc every undisclosed vendor floats to the top and your top three becomes three empty rows. Two remedies exist:

order by funding_usd_m desc nulls last   -- keep the rows, push them down
where funding_usd_m is not null          -- exclude them entirely

Choose according to meaning. "Best funded" excludes the unknown. "All vendors, best funded first" keeps them and demotes them. Deciding which question you are answering is the actual skill; the syntax takes a minute.

Also note that limit without order by is non-deterministic. Postgres will happily return three arbitrary rows, and will return a different three after a vacuum.

7. Block B — Combining tables

Drill 3 · Join across the foreign key

Brief. Every funding round with the vendor it belongs to: vendor name, stage, amount, lead investor.

select v.name, r.stage, r.amount_usd_m, r.lead_investor
from rounds r
join vendors v on v.id = r.vendor_id;

Returns 7 rows.

Coaching. Driving from rounds rather than from vendors reflects the question. You want rounds, annotated with vendor names, so rounds is the left-hand table and join (inner by default) keeps exactly the rounds that resolve.

Try from vendors v left join rounds r on r.vendor_id = v.id and observe fourteen rows instead of seven, most padded with nulls. Neither is wrong; they answer different questions. Choosing a join type is choosing which side is allowed to be absent.

One row in the output has NULL in both amount and lead investor: a Series E that the source reporting confirms happened without disclosing terms. Presence and value are separate facts, and a database that conflates them will lie to you.

Drill 4 · Aggregate, then filter the groups

Brief. Total disclosed funding by engine type, keeping only engine types with at least two disclosing vendors.

select engine, sum(funding_usd_m) as total
from vendors
where funding_usd_m is not null
group by engine
having count(*) >= 2;

Returns: key-value 367, postgres 141.2.

Coaching. Three filters could apply, at three different moments, and knowing the order matters more than memorising the keywords.

  1. where runs first, on individual rows, before any grouping exists.
  2. group by collapses rows into groups.
  3. having runs last, on the groups, and can see aggregates.

Writing where count(*) >= 2 raises an error because count(*) does not exist yet when where executes. Writing having funding_usd_m is not null fails differently, because after grouping there is no single row to test.

Notice what the result understates. Postgres shows 141.2 million and omits Supabase entirely, whose Series F alone was 500 million, because no total-raised figure appeared in the reporting. An aggregate over sparse data produces a number with a shape and a wrong magnitude, and it will be quoted by someone who never saw the where clause. Label such outputs "disclosed total" and never "total".

8. Block C — Postgres beyond SQL-92

Drill 5 · Rank inside a partition

Brief. Best-funded vendor within each engine type, one row per engine.

with ranked as (
  select engine, name, funding_usd_m,
         row_number() over (partition by engine order by funding_usd_m desc) as rn
  from vendors
  where funding_usd_m is not null
)
select engine, name, funding_usd_m
from ranked
where rn = 1;

Returns 5 rows: custom/Convex, duckdb/MotherDuck, key-value/Redis, postgres/Neon, sqlite/Turso.

Coaching. Window functions compute across a set of rows while leaving those rows intact, which is precisely what group by refuses to do. partition by slices the table; order by inside the over clause orders each slice independently.

Filtering on the result needs a second query level, hence the CTE. A window function is evaluated after where, so where rn = 1 in the same select that defines rn cannot work. Subquery or CTE, either is fine; the CTE reads better and costs nothing.

Pick your ranking function deliberately:

Function Behaviour on ties
row_number() Arbitrary but distinct numbering. Two tied rows get 1 and 2.
rank() Ties share a number, then the sequence skips. 1, 1, 3.
dense_rank() Ties share a number, no gap. 1, 1, 2.

row_number() with a tie gives you one winner chosen at random and no warning that a coin was flipped. Add a tiebreaker to the order by when determinism matters.

Drill 6 · Reach into JSONB

Brief. Every vendor whose meta records branching as true.

select name
from vendors
where meta @> '{"branching":true}';

Returns: Neon, Supabase, Prisma Postgres.

Coaching. Two workable approaches, with different properties.

where meta @> '{"branching":true}'     -- containment; GIN-indexable
where meta ->> 'branching' = 'true'    -- extract as text; compares strings

Containment tests whether the left document contains the right one, respects JSON types, and can use a GIN index. Extraction with ->> returns text, which means a JSON true and a JSON string "true" become indistinguishable, and no index helps. Reserve ->> for pulling a value out to display, and use @> when filtering.

Keep the difference between -> and ->> in mind: the first returns jsonb and chains, the second returns text and terminates.

Larger point about jsonb itself: it is a legitimate answer to genuinely irregular data and a very popular way to avoid schema design. When the same key appears in most rows and gets queried often, promote it to a real column. You gain type checking, constraints, cheaper indexes and a schema that documents itself.

9. Block D — Operating the database

Drill 7 · Create an index and read the plan

Brief. Create a btree index named idx_vendors_engine on vendors(engine).

create index idx_vendors_engine on vendors (engine);

Verification. Checked against pg_indexes rather than a result set, since DDL returns no rows.

Coaching. Now run the interesting part:

explain analyze select * from vendors where engine = 'postgres';

Postgres ignores your index and performs a sequential scan. Correct behaviour: on fourteen rows spanning one page, reading everything costs less than consulting an index and then fetching rows. A planner that used every available index would be a worse planner.

Understanding that refusal is the drill. Indexes earn their place when selectivity is high and the table is large; each one you add taxes every insert, update and delete, and consumes storage that on consumption billing appears on an invoice. pg_stat_user_indexes will show you which indexes in a real system have never been scanned, and the number is usually higher than anyone expects.

Read explain analyze output from the innermost node outward. Compare the planner's estimated row counts against actual counts; large divergence usually means stale statistics, and analyze is the first thing to try.

Drill 8 · Write a row-level security policy

Brief. Enable RLS on vendors, then grant public read access via a policy named public_read.

alter table vendors enable row level security;
create policy public_read on vendors for select using (true);

Verification. Checked against pg_policies.

Coaching. Worth more attention than any other drill on the floor, because it is core Postgres, it is fully portable, and Supabase builds an entire authorisation model on top of it. Learn it here and you have learned a large part of Supabase before opening an account.

Mechanics. enable row level security switches the table to deny-by-default for ordinary roles. Policies then add back specific permissions. A using clause governs which existing rows a role may see or modify; a with check clause governs which new rows a role may write. Omitting with check on an insert or update policy is a standard way to build a table that correctly hides other tenants' rows and cheerfully lets anyone create rows belonging to them.

Two traps to carry into production:

  • Superusers bypass RLS entirely, and so does the table owner unless you also issue alter table vendors force row level security. Testing a policy while connected as the owner proves nothing. PGlite connects you as superuser, so this drill can confirm that a policy exists but cannot demonstrate that it works.
  • Policies are evaluated per row. A policy calling a function or subquery runs it for every candidate row. Index the columns your policies test, or watch a simple query degrade badly at scale.

10. The full programme: what a complete floor looks like

Eight drills demonstrate the mechanism. A credible curriculum needs roughly forty to sixty, and the blocks below sketch the shape. Everything listed here is portable Postgres and can run entirely in the browser.

Block A — Reading rows (6–8 drills). Projection, predicates, three-valued logic, is distinct from, pattern matching, coalesce, case, ordering with collations, limit with offset and why keyset pagination beats it.

Block B — Combining tables (8–10 drills). All join types, self-joins, anti-joins via not exists versus not in and the NULL trap that separates them, set operations, group by with rollup and grouping sets, filter on aggregates, distinct on as a Postgres-specific shortcut.

Block C — Beyond SQL-92 (10–12 drills). Window frames beyond the default, running totals, lag and lead, recursive CTEs, arrays, ranges and exclusion constraints, full-text search with tsvector, jsonb paths and generated columns, pgvector similarity search with an HNSW index.

Block D — Operating (8–10 drills). Index types and when each applies, partial and expression indexes, reading explain analyze, statistics and analyze, transaction isolation levels, select for update, deadlock reproduction, constraints as documentation, RLS with multiple roles, pg_stat_statements.

Block E — Change over time (6–8 drills). Migrations as ordered, reversible, reviewed artefacts. Adding a column safely under load, backfilling without a long lock, alter table operations that rewrite versus those that do not, expand-contract deployment, and rehearsing a restore rather than assuming one.

Block E cannot be fully exercised in a single-connection browser engine. Blocks A through D can.

11. Codd's twelve rules, tested

Codd published twelve rules in Computerworld in October 1985, defining what a system must do to call itself relational. The practice floor carries a tier that judges Postgres against each one and provides a demonstration you can run.

Findings, in brief. Nine honoured: the information rule, the catalog rule, the comprehensive sublanguage, set-at-a-time writes, physical data independence, integrity independence, and the foundation rule. Three partial: guaranteed access, since duplicate rows are permitted; view updating, since only simple views update through; and nonsubversion, since a superuser can suspend foreign key enforcement. One failed: systematic treatment of nulls, where Codd wanted two marks and SQL supplies one. One untestable on a single node: distribution independence, which remains the live commercial problem forty years on.

Rules 8, 9 and 12 are arguments that logical meaning must stay independent of implementation. That is the same case as the transfer ratings in section 12, made twenty-five years earlier and with better foundations.

Sources. The ACM Digital Library became fully open access on 1 January 2026, so Codd's papers are free to read. A Relational Model of Data for Large Shared Data Banks, CACM 13(6), 1970, at doi.org/10.1145/362384.362685. On nulls specifically, Missing Information (Applicable and Inapplicable) in Relational Databases, SIGMOD Record 15, 1986. The twelve rules appeared in trade press rather than in ACM and are restated rather than reproduced.

12. The machines: platform training briefs

One machine at a time. Each brief assumes the floor is complete and states what to build, what it costs, and what leaves with you.

Neon — branching

Owner: Databricks, acquired for roughly $1bn in May 2025. Transfer rating 85%.

Copy-on-write storage makes a branch a metadata operation rather than a copy, so a database branch costs about what a Git branch costs. Compute suspends when idle.

Session. Provision a project. Create a branch from main and observe the elapsed time. Load a few hundred thousand rows, branch again, confirm that storage barely moves. Wire branch-per-pull-request into a CI pipeline so every review gets an isolated database seeded with production-shaped data. Let a branch idle and watch compute scale to zero. Reset a branch from its parent after deliberately corrupting it.

Leaves with you. Branch-per-environment as a working practice; you will want it everywhere afterwards. Stays behind. Neon's branch API and console.

Docs: neon.com/docs · Branching: neon.com/docs/introduction/branching

Supabase — row-level security and the generated API

Independent. $500m Series F led by GIC at $10.5bn post-money, June 2026. Transfer rating 70%.

Postgres surrounded by auth, storage, realtime subscriptions and Deno-based edge functions. PostgREST exposes tables as a REST API directly from the schema.

Session. Design a two-tenant schema. Write RLS policies for select, insert, update and delete, each with both using and with check where applicable. Create two users and verify from each side that isolation holds. Only then enable the generated API and confirm that policies govern it, because PostgREST enforces nothing on its own. Add a realtime subscription. Store embeddings with pgvector and query them with plain SQL alongside relational columns.

Leaves with you. The RLS work, entirely: it is core Postgres. Stays behind. Supabase Auth, Storage, Edge Functions and the client SDK.

Docs: supabase.com/docs · RLS: supabase.com/docs/guides/database/postgres/row-level-security

Amazon Aurora PostgreSQL — procurement reality

Amazon Web Services. Transfer rating 65%.

Default corporate answer, and the one that clears an enterprise review without argument. Regained scale-to-zero capability in late 2024 and became discountable through Database Savings Plans introduced December 2025.

Session. Provision Serverless v2 inside a VPC. Configure IAM database authentication rather than a password. Change a parameter group and note which changes force a restart. Create a read replica and measure lag. Restore to a point in time. Price the same workload against Neon and Supabase, then price it again including the engineering hours the VPC and IAM work consumed.

Leaves with you. Postgres tuning, replication concepts. Stays behind. VPC topology, IAM policy, parameter groups, Savings Plan commitments.

Docs: docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/

Aurora DSQL — distributed writes

Amazon Web Services. Generally available May 2025. Transfer rating 55%.

Postgres-compatible distributed SQL with multi-region strong consistency, billed by distributed processing unit.

Session. Provision a multi-region cluster. Write to two regions concurrently and confirm both reads agree. Then find the limits: DSQL restricts several things ordinary Postgres allows, and the restrictions are the product. Measure write latency against single-region Aurora and decide whether your application genuinely requires global writes, since most do not.

Leaves with you. A grounded sense of what distributed consensus costs. Stays behind. Everything else.

Docs: docs.aws.amazon.com/aurora-dsql/

Prisma Postgres — schema as code

Independent, funding position undisclosed. Transfer rating 70%.

A TypeScript ORM company moved down the stack into hosting, running on unikernel microVMs and billing per operation.

Session. Model a schema in Prisma's DSL, generate and apply migrations, then read the SQL those migrations produced and judge it. Introspect an existing database into a schema file. Price a read-heavy workload under per-operation billing against per-hour billing elsewhere; the crossover point is the lesson.

Leaves with you. Migrations as reviewed, versioned artefacts. Stays behind. Prisma's DSL and client. Note that the corporate funding position is undisclosed, which is information in itself for a long-lived dependency.

Docs: prisma.io/docs/postgres

Nile — multi-tenancy as a primitive

Independent. $11.6m seed led by Benchmark. Transfer rating 60%.

The tenant is built into Postgres rather than bolted on with a tenant_id column and vigilance.

Session. Build the same two-tenant schema twice: once with conventional columns plus RLS, once with Nile's tenant primitive. Compare query ergonomics and the number of places a bug could leak data across tenants. Then weigh a seed-stage supplier against a production dependency, which is a commercial judgement rather than a technical one.

Docs: thenile.dev/docs

Turso — many small databases

Independent, roughly $7m seed. Transfer rating 60%.

SQLite rewritten from scratch in Rust, adding concurrent writes and vector search, with an experimental Postgres frontend launched July 2026.

Session. Provision a database per user rather than per application and note how the mental model shifts: backups, migrations and quotas all become per-tenant problems with per-tenant solutions. Test the Postgres frontend and treat "experimental" as accurate.

Docs: docs.turso.tech

Convex — a different bargain

Independent. $24m led by Andreessen Horowitz, co-led by Spark Capital. Transfer rating 20%.

Schema, queries, authorisation and scheduled work all expressed in TypeScript, reactive by default.

Session. Build a collaborative document editor where several people see the same change simultaneously. Then build it again on Postgres with a websocket layer and count the assembly work Convex removed. That comparison is the only honest way to evaluate a 20% transfer rating: the question is whether what you gain now outweighs a migration you cannot perform later.

Docs: docs.convex.dev

DynamoDB — access patterns first

Amazon Web Services. Transfer rating 15%.

Heaviest switching cost in the field. On-demand throughput pricing halved in November 2024 and replicated write costs for global tables fell by up to 67%.

Session. Enumerate every access pattern your application needs before creating a table, because that ordering is compulsory here. Design a single-table layout with composite keys and a global secondary index. Then invent a new access pattern nobody anticipated and discover what it costs. Single-table design is a genuine skill and a genuine trap, and doing it once teaches you which of your workloads should never leave SQL.

Docs: docs.aws.amazon.com/amazondynamodb/

Redis and Valkey · Upstash · MongoDB Atlas · MotherDuck

Shorter briefs, same method.

Redis / Valkey (75%): expiry and eviction policy, cache-aside versus write-through, and confirming that your commands run unchanged against the Linux Foundation fork created after the 2024 licence change. Portability was the entire point of that fork.

Upstash (70%): per-request billing for cache, queue and vector, so idle infrastructure costs nothing. Model a spiky workload and find where per-request economics stop beating a provisioned instance.

MongoDB Atlas (25%): document modelling and the aggregation pipeline, which is entirely its own vocabulary. Worth study as the only challenger with audited figures — FY2026 revenue of $2.46bn with Atlas growing 29% — against which private valuations elsewhere can be sanity-checked.

MotherDuck (70%): DuckDB is free, local and close enough to Postgres SQL to feel familiar. Load a dataset larger than memory, then decide honestly whether your organisation ever had the data volumes that justified a distributed warehouse.

13. Spotters: giving an agent database access without regret

Three patterns cover the field.

Native. Platform ships one database and hides the wiring. Lovable and Bolt.new default to Supabase; Replit Agent embeds managed Postgres; v0 provisions from Vercel's marketplace; Databricks bought Neon outright and folded it in as Lakebase. Fastest path to a running application, and the database ends up chosen by whoever wrote the platform's integration rather than by you.

MCP. More consequential development. Model Context Protocol servers let a coding agent — Claude Code, Cursor, Windsurf, VS Code — inspect schema and execute queries against a database you already own. Neon's server offers branch-based migration safety and runtime scoping headers. Supabase ships OAuth-based MCP. Postgres MCP Pro handles self-hosted instances with index tuning and plan analysis. DBHub covers several engines at a fraction of the token cost. Google's MCP Toolbox spans 40+ data sources.

BYO. Paste a connection string into a chat window. No provisioning, no scoping, and all of the risk.

Safety practice, in order

  1. Start read-only. Every database MCP server worth using ships a read-only mode. Use it for a week before considering anything else.
  2. Scope the credential, not the intention. Grant a role with the narrowest privileges on one schema. A prompt asking an agent to be careful is not an access control.
  3. Write access only against a restorable database. Branch it, or point at a copy. Neon's branch-based migration flow exists for exactly this and is the standout feature in the category.
  4. Read the tool list. Servers expose twenty to thirty tools. Know which ones drop things.
  5. Assume the context is hostile. An agent reading query results is reading data that other people wrote. Treat retrieved content as data, never as instructions.

Vercel's own history supplies the closing argument: an OAuth supply-chain compromise at a third-party tool exposed unencrypted environment variables across its ecosystem. Credentials handed to an integration are credentials handed to everyone that integration trusts.

14. Maintenance protocol: keeping this from rotting

Half of this manual will still be accurate in 2036. The other half has a shelf life measured in months, and mixing them without labels is how a teaching resource becomes a source of misinformation.

Effectively permanent. Sections 3 and 6 to 10. SQL semantics, NULL behaviour, window functions, indexing, RLS mechanics. Postgres changes by addition; almost nothing here will be invalidated.

Review every six months. Section 12 training sessions. Console flows and feature names drift; the underlying exercises rarely do.

Review quarterly, and date every claim. Ownership, funding, valuation, pricing, transfer ratings. Recent months alone brought a $1bn acquisition, a $500m round at $10.5bn, a $300m ARR disclosure followed by layoffs, an experimental Postgres frontend from a twenty-person company, and one major platform exiting storage to become a broker. A card asserting a 2026 fact in 2027 is worse than a card asserting nothing.

Implementation note. Volatile facts live in exactly two places in the prototype: the MACHINES array and the SEED string, both in the single JavaScript block. Regenerating both from a fresh source review is a contained task. Keeping them contained is the maintenance design, and scattering vendor claims into prose would undo it.

Appendix A — Quick reference card

Clause execution order, which differs from writing order and explains most confusing errors:

from → where → group by → having → select → window → order by → limit

Null handling

coalesce(x, 0)              -- substitute a default
nullif(x, '')               -- turn a sentinel back into NULL
x is distinct from y        -- equality that treats NULL as a value
count(*) vs count(col)      -- second one skips NULLs
order by col desc nulls last

Joins

inner join   -- rows matching on both sides
left join    -- all left rows, nulls where no match
full join    -- everything, nulls on both sides as needed
where r.id is null           -- after a left join: the anti-join
not exists (select 1 ...)    -- anti-join that survives NULLs
not in (select ...)          -- returns nothing if the subquery yields one NULL

Windows

row_number() over (partition by a order by b)
rank() | dense_rank() | lag(x, 1) | lead(x, 1)
sum(x) over (order by d rows between unbounded preceding and current row)

JSONB

meta -> 'k'                  -- returns jsonb, chains
meta ->> 'k'                 -- returns text, terminates
meta @> '{"k":true}'         -- containment, GIN-indexable
jsonb_path_query(meta, '$.a.b')

Operations

explain (analyze, buffers) select ...;
create index concurrently ... ;          -- no write lock, slower
create index ... where active;           -- partial index
select * from pg_stat_user_indexes;      -- find unused indexes
alter table t enable row level security;
alter table t force row level security;  -- applies to the owner too
create policy p on t for select using (tenant_id = current_tenant());

Appendix B — Glossary

Branching — creating an isolated copy of a database via metadata rather than by copying bytes, so cost and elapsed time stay near zero regardless of size.

Consumption billing — charging by units used (compute-hour, request, operation, distributed processing unit) rather than by provisioned capacity.

CTE — common table expression, a named subquery introduced by with, used here to make window-function results filterable.

GIN index — generalised inverted index, suited to containment queries over jsonb, arrays and full-text vectors.

HNSW — hierarchical navigable small world, the graph index pgvector uses for approximate nearest-neighbour search.

MCP — Model Context Protocol, a specification for exposing tools and data to language models, and currently the main route by which coding agents reach databases.

pgvector — Postgres extension storing embedding vectors and running similarity search in SQL, removing the need for a separate vector database in many applications.

PGlite — Postgres compiled to WebAssembly by ElectricSQL, under 3MB gzipped, running the practice floor.

Row-level security — Postgres feature restricting which rows a role may see or modify, enforced by the database rather than by application code.

Scale to zero — suspending compute entirely when a database is idle, so an unused database costs only storage.

Transfer rating — this manual's editorial estimate of how much of the training on a given platform survives a move to a different supplier.

Wire compatibility — implementing the Postgres client-server protocol, so existing drivers, ORMs and tools connect without modification. The organising fact of the current market.
